## 1. Core Philosophy, 84-Slot Weekly Matrix Math & Scheduling Window

Vismatix is a structured digital publishing operating system that replaces unorganized spreadsheets and date-picker guesswork with an **84-Slot Weekly Execution Matrix**.

- **Grid Dimensions:** `7 days × 12 two-hour time blocks = 84 weekly slots`.
- **Day Index Mapping (`day_of_week`):**
  - `1` = Sunday | `2` = Monday | `3` = Tuesday | `4` = Wednesday | `5` = Thursday | `6` = Friday | `7` = Saturday
- **Slot Index Mapping (`time_slot`, 2-hour windows in the user's configured timezone):**
  - `1` = `00:00–02:00` | `2` = `02:00–04:00` | `3` = `04:00–06:00` | `4` = `06:00–08:00` *(Off-Peak night/early window)*
  - `5` = `08:00–10:00` | `6` = `10:00–12:00` | `7` = `12:00–14:00` *(Top Midday Prime)* | `8` = `14:00–16:00`
  - `9` = `16:00–18:00` | `10` = `18:00–20:00` *(Top Evening Peak)* | `11` = `20:00–22:00` *(Night Peak)* | `12` = `22:00–24:00` *(Late Off-Peak)*
- **Prime Slots Preference Order (`PRIME_SLOTS`):** `[7, 10, 8, 11, 6, 9, 5]`. Auto-scheduler and rebalancer rank these slots highest; slots `< 5` (`00:00–08:00`) and `12` (`22:00–24:00`) trigger off-peak health penalties.
- **Hard Scheduling Window (`ScheduleDateTimeWindow`):**
  - **Minimum Lead Time:** Scheduled timestamps MUST be **at least `60` minutes in the future** (`now()->addMinutes(60)`), otherwise validation fails with `422`.
  - **Maximum Horizon:** Cannot exceed **`12` months (`1` year)** ahead of current time.
  - **DST Ambiguity Protection:** Ambiguous or nonexistent local wall-clock times during Daylight Saving transitions are rejected rather than silently shifted.
- **Four Strategic Publishing Pillars (Default Content Mix):**
  - **Anchor Content (30%):** Deep case studies, frameworks, reference guides (morning/midday focus windows).
  - **Velocity Bursts (35%):** Concise high-save tactical observations, teardowns, quick checklists.
  - **Community Flywheel (20%):** Questions, polls, open discussions driving comments and replies.
  - **Conversion & Launches (15%):** Product releases, lead magnets, and UTM-tracked offers in proven peak slots.
- **Auto Time-Block Resolution:** When scheduling via API (`POST /api/v3/posts` or `/posts/batch`), agents may supply `scheduled_datetime` (ISO-8601 string or normalized user-timezone datetime) and omit `time_block_id` — Vismatix automatically resolves or provisions the matching weekly `agenda_id` and `time_block_id`.
- **Post Lifecycle States:** `idea` -> `draft` (safe editable copy, never auto-published) -> `scheduled` (queued for automated publishing at `scheduled_datetime`) -> `published`. Transitional async states during active dispatch are `publishing` and `awaiting_verification` (used for interactive browser 2FA/checkpoint flows).
- **Content Safety Versions & Snapshots:** Every post supports manual/automated copy snapshots (`GET/POST /posts/{id}/snapshots`, `POST /posts/{id}/restore-snapshot`), bulk status/delete/tag/reschedule mutations, and upcoming pre-publish notifications.

## 5. AI Token Consumptions, 3-Bucket Deduplication, Reserve Vault & Averages

### 5.1 The 3-Bucket Execution & Deduplication Rules
Every Vismatix account enforces atomic, concurrency-safe token accounting across three ordered buckets:

1. **System 1 — 5-Hour Burst Window:** Rolling 5-hour cap (`4,000` Starter .. `175,000` Ultra). Expires **5 hours after the oldest usage event** inside the active window.
2. **System 2 — Weekly Cycle Window:** Resets every 7 days with **zero rollover** (`rollover_enabled: false`).
3. **System 3 — Non-Expiring Reserve Vault (`/settings/usage`):** Persistent token bank starting at `0`, funded by purchasing configured token packs with the existing GC wallet balance, and **never expires**. A pack purchase debits GC; it does not charge a card or create new GC.
4. **Anti-Double-Charging Deduplication Rule:**
   - Tokens consumed by a request deduct from the included System 1 (5-hour) allowance **first**, then from paid 5-hour refill credits.
   - System 2 (Weekly) is only charged `max(0, chargedTokens - usedFromFiveHourRefill)` — ensuring **paid Reserve tokens spent in the 5-hour window are never deducted twice** against your weekly quota.
   - Launching **4 HOXI Ultra Mode** requires `min_ultra_tokens >= 2,000` combined available tokens (active window + eligible auto-refill headroom).

### 5.2 Credit Packs

Each purchase requires a unique `Idempotency-Key` (reuse it only for an exact retry), debits the listed GC amount once, and adds tokens to the non-expiring Reserve Vault. ## 6. Exact Algorithmic Formulas: Schedule Health, Rebalancer, ROI, Cadence, HookMeter & GEO

### 6.1 Schedule Health Score Formula (`0–100`)
Evaluated across upcoming scheduled posts and the next 7 calendar days:
- **Starting Baseline:** `100`
- **Deductions:**
  - **`-15` per slot collision:** Multiple scheduled posts occupying the same date + 2-hour `time_slot`.
  - **`-8` per off-peak scheduled post:** `time_slot < 5` (`00:00–08:00`) or `time_slot == 12` (`22:00–24:00`).
  - **`-15` per approval blocker:** Scheduled post stuck in `approval_status` = `pending_review` or `rejected`.
  - **`-5` per excessive platform crowding:** Each post beyond `2` posts for the same platform on the same calendar day (`excess * 5`).
  - **`-3` per empty day in next 7 days:** Capped at `min(4, emptyDays) * 3` (`-12` max).
- **Status Classification:** `>= 80` -> `healthy` | `55–79` -> `needs_attention` | `< 55` -> `critical`.

### 6.2 Auto-Rebalancer, Recurring Templates & ROI Formulas
- **Transactional Rebalancer (`Pro+`, Matrix Studio):**
  - Automatically skips posts currently awaiting manual verification, and relocates colliding or off-peak posts up to **`14` days ahead** into open `PRIME_SLOTS = [7, 10, 8, 11, 6, 9, 5]` while respecting the **`+60 minutes` .. `+12 months`** schedule window.
- **Recurring Matrix Templates (`Pro+`):**
  - Stamps multi-day slot blueprints into the target project's weekly `Agenda`, marking `is_peak_hour = true` automatically for slots `7–11` (`12:00–22:00`).
- **ROI Rollup & Evergreen Lift (`Pro+` Strategy Radar):**
  - `estimated_hours_saved = round((publishedPosts * 0.25) + (totalRecycledRuns * 0.5), 1)` (`15 min` saved per scheduled publish + `30 min` per automated evergreen recycle).
  - `evergreen_lift.output_multiplier = round((evergreenCount + totalRecycledRuns) / evergreenCount, 2)`.

### 6.3 Cadence Health Score Formula (`0–100`, `GET /api/v3/analytics/overview`)
- **Starting Baseline:** `50`
- **Bonuses (Capped at `100`):**
  - **`+30`** if `scheduled >= 7` posts (or **`+15`** if `3 <= scheduled < 7`)
  - **`+10`** if spanning `>= 3` active platforms
  - **`+10`** if `>= 1` post occupies a Golden Peak Hour (`is_peak_hour = true`)

### 6.4 HookMeter Simulator and API Editorial Audit
The `/docs/hookmeter` simulator starts at 20, adds 25 for a trimmed first line of 25–130 characters (otherwise 12 for a nonempty first line), 20 for digits anywhere, 18 for a blank line and 17 for a CTA signal, capped at 100. Its range is 20–100.

`POST /api/v3/posts/virality-audit` uses a separate editorial heuristic, not a prediction of reach. It starts hook at 50; adds 15 for a digit, 15 for a whole-word trigger (`why`, `how`, `what`, `secret`, `revealed`, `stop`, `never`, `always`) and 10 for `?`, `!` or supported emoji in the title's first line; caps hook at 100. Structure is 85 when description exceeds 100 characters and 70 otherwise. CTA is 90 when description contains a whole-word `comment`, `bookmark`, `save`, `reply`, `click`, `link` or `share`, otherwise 60. The overall score is `round(0.4 * hook + 0.3 * structure + 0.3 * CTA)`; grades are A+ (>=85), A (>=75), B (>=65), otherwise C. `virality_score` is null and `score_type` is `editorial_heuristic`.

### 6.5 Generative Engine Optimization (GEO) Formula (`0–100`, `POST /api/v3/geo/analyze`)
Prepares articles, guides, and posts so AI engines extract accurate brand citations (`/docs/geo`, `GET /api/v3/geo/guidelines`):
- **5 Weighted Pillars (Total `100` pts):**
  1. `direct_answer_score` (`0–25`): `5` base + `5` question-style heading + `8` concise opening (`8–50` words) + `7` definitive verbs (`is`, `means`, `refers to`, `provides`).
  2. `quotability_score` (`0–25`): Concise `10–35` word standalone declarative sentences easy for RAG citation extraction.
  3. `entity_density_score` (`0–20`): Up to 6 verifiable numeric benchmarks (`× 2` pts) + named technical entities & dates.
  4. `eeat_score` (`0–15`): First-party methodology markers, empirical attribution, named author (`author` field).
  5. `structure_score` (`0–15`): Valid headings, structured bullet takeaways, JSON-LD readiness (`TechArticle`, `FAQPage`, `SpeakableSpecification`), `/llms.txt` & `/llms-full.txt` support.
- **Grade Scale:** `A+` (`>= 90`) | `A` (`80–89`) | `B` (`70–79`) | `C` (`60–69`) | `D` (`< 60`).
- **Tracked AI Crawlers:** `GPTBot`, `ChatGPT-User`, `PerplexityBot`, `ClaudeBot`, `Google-Extended`, `Applebot-Extended`.

## 8. Developer REST API v3 Security, Keys, Rate Limits, Wallet & Idempotency

### 8.1 Authentication Headers & Dual-Tier Keys (`/docs/developer/keys`)
Pass a valid key on every protected route via either header:
- `Authorization: Bearer <API_KEY>` (recommended) or `X-API-Key: <API_KEY>`
- Always send `Accept: application/json`.

**Dual-Tier Key Architecture:**
1. **`vmtx_u_...` (Account Master Key):** Full account power across all owned workspaces, `/account/*`, `/projects`, `/wallet*`, `/webhooks*`, `/notifications*`, `/presets*`, `/audit-logs*`, and admin-verified `/ai*` routes.
2. **`vmtx_p_...` (Project Restricted Key):** Pinned strictly to one `project_id`. Allowed on `/projects/{id}`, `/posts*`, `/matrix*`, `/tasks*`, `/ideas*`, `/analytics*`, `/templates*`.
   - **Hard Isolation:** Calling `/account*`, `/audit-logs*`, `/wallet*`, `/webhooks*`, `/notifications*`, `/presets*`, or `/ai*` (or passing another `project_id`) with a `vmtx_p_` key returns **HTTP `403 FORBIDDEN_PROJECT_KEY`**.

### 8.2 Optional Request HMAC Signature (`X-Vismatix-Signature`)
For high-security clients, incoming API v3 requests can optionally include:
- Header format: `X-Vismatix-Signature: t=<unix_timestamp>,v3=<hex_hmac_sha256>`
- Maximum clock drift: `300` seconds (`TIMESTAMP_OUT_OF_BOUNDS` otherwise).
- Signed string: `"{timestamp}.{METHOD}.{path_without_leading_slash}.{sha256_hex(raw_body)}"` keyed with your secret signing credential.

### 8.3 Infrastructure & Edge Protection
- **Adaptive Edge Protection & Anti-Abuse Guard:** All public/API routes apply adaptive burst, sustained rate-limit, SSRF validation, and confirmed-anonymizer edge filtering while keeping residential and mobile traffic clean, returning HTTP **`429 RATE_LIMITED`** + `Retry-After` and `Cache-Control: no-store, private` when exceeded.

## 10. Webhooks, HMAC-SHA256 Verification & SDKs

- **Supported Webhook Events:** `post.created`, `post.scheduled`, `post.published`, `task.completed` (SSRF protection blocks localhost/loopback/private IP targets with `422 SSRF_BLOCKED`).
- **Outbound Signature Header:** `X-Vismatix-Signature: t={unix_timestamp},v2={hex_hmac_sha256}` where HMAC signs `"{timestamp}.{raw_json_body}"` using your webhook's `secret`.
- **Verification Snippet (Python):**
  ```python
  import hmac, hashlib

  def verify_vismatix_webhook(raw_body: bytes, sig_header: str, secret: str) -> bool:
      parts = dict(item.split("=", 1) for item in sig_header.split(",") if "=" in item)
      ts, sig = parts.get("t", ""), parts.get("v2", "")
      signed = f"{ts}.".encode("utf-8") + raw_body
      expected = hmac.new(secret.encode("utf-8"), signed, hashlib.sha256).hexdigest()
      return bool(ts and sig and hmac.compare_digest(expected, sig))
  ```
- **Verification Snippet (Node.js):**
  ```javascript
  import crypto from 'node:crypto';

  export function verifyVismatixWebhook(rawBodyBuffer, sigHeader, secret) {
    const parts = Object.fromEntries(sigHeader.split(',').map((p) => p.split('=')));
    if (!parts.t || !parts.v2) return false;
    const signed = Buffer.concat([Buffer.from(`${parts.t}.`, 'utf8'), rawBodyBuffer]);
    const expected = crypto.createHmac('sha256', secret).update(signed).digest('hex');
    return expected.length === parts.v2.length && crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(parts.v2));
  }
  ```

###### Verifying X-Vismatix-Signature (Python & Node.js)

Every outbound webhook delivery sets `X-Vismatix-Signature: t=TIMESTAMP,v2=HEX_SIGNATURE` where `v2 = HMAC_SHA256(secret, "{t}.{raw_body}")` .

```
# Python Verification
import hmac, hashlib

def verify_webhook(raw_body: bytes, sig_header: str, secret: str) -> bool:
    parts = dict(p.split("=", 1) for p in sig_header.split(",") if "=" in p)
    t, v2 = parts.get("t", ""), parts.get("v2", "")
    signed = f"{t}.".encode("utf-8") + raw_body
    digest = hmac.new(secret.encode("utf-8"), signed, hashlib.sha256).hexdigest()
    return bool(t and v2 and hmac.compare_digest(digest, v2))
```

```
// Node.js Verification
import crypto from 'node:crypto';

export function verifyWebhook(rawBuffer, sigHeader, secret) {
  const parts = Object.fromEntries(sigHeader.split(',').map((s) => s.split('=')));
  if (!parts.t || !parts.v2) return false;
  const payload = Buffer.concat([Buffer.from(`${parts.t}.`), rawBuffer]);
  const expected = crypto.createHmac('sha256', secret).update(payload).digest('hex');
  return expected.length === parts.v2.length &&
         crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(parts.v2));
}
```
